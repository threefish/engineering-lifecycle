# 数据访问

> 加载时机：涉及查询、存储实体、表结构变更、批量操作、数据修复的改动前读取。

## 1. 分层收口

- 所有持久化访问经基础设施层；业务层只面对数据访问接口，不感知存储细节。
- 查询构造与 SQL 集中在数据访问层；业务层不得手工拼 SQL。
- 对象转换（存储实体 ↔ 业务/传输模型）用统一映射机制，禁止散落的逐字段手工拷贝。

## 2. 查询边界

- 任何查询必须有边界：条件、上限或分页；禁止无 WHERE 的全量读取进入内存。
- 列表接口默认有序、有上限；导出/批处理走游标或分批。
- 全表更新/删除：条件必须明确、影响行数必须预估、执行必须经当次确认。

## 3. 软删除与默认过滤

- 逻辑删除策略项目内统一（字段、取值、生效范围）。
- 普通查询默认过滤已删除数据；需要读取已删除数据时显式声明意图。

## 4. 审计字段

- 创建人、创建时间、修改人、修改时间由统一机制自动填充，不信任请求体传入。
- 数据修复类操作同样必须留痕（谁、何时、依据什么）。

## 5. 表结构变更

- 变更通过迁移脚本管理：可评审、可回放、可回滚；禁止依赖自动建表直接上生产。
- 新增列优先可空或带默认值，避免锁表与存量数据不一致。
- 回滚脚本与变更脚本一起交付。

## 6. 类型与存储一致性

- 时间统一时区与存储类型；金额用整数最小单位存储。
- 大字段、JSON 集合、枚举的存储策略项目内保持一致，同一概念不出现两套存法。
- 枚举入库用稳定编码，展示名可改不可作键。

## 7. 性能

- 查询与索引匹配：先看执行计划，再改代码。
- 性能问题先定位根因（缺失索引、错误谓词、N+1、大结果集），不得用缓存掩盖。
- 缓存是加速手段不是正确性依赖：失效路径、一致性影响必须说明。
