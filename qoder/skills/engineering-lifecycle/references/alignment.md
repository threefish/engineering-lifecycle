# 需求对齐与问题定义

> 加载时机：需求不清晰、需要划定范围、要出方案供用户决策前读取。轻量改动（单点小改、文案修正）不必加载。

## 1. 只问「影响决策」的问题

- 问之前先自查：能否通过读代码、看文档、查历史自行回答？能答则不问。
- 一轮集中提问，不超过 3–5 个；每个问题带默认值或推荐项，不无限追问。
- 优先选项式提问：2–4 个互斥选项 + 推荐项前置 + 每个选项写清代价与后果。

## 2. 对齐的是约束与偏好，不是细节

- **必须对齐**：目标与非目标、验收标准、不可动的边界（兼容 / 合规 / 数据）、时间与质量的取舍。
- **不必对齐**：命名、内部结构等可按项目规范自行决定的事项。

**对齐产出**：一段可复述的需求摘要 + 明确的 Non-goals（明确不做什么）。确认后范围锁定，自主推进，不再逐步请示。

## 3. 重大决策出 3 版方案

当方案空间存在真实分歧（架构、契约、数据模型、交互习惯）时给出：

| 版本 | 定位 | 必须说明 |
|---|---|---|
| A 稳妥版 | 最小改动、最快落地 | 明确牺牲了什么 |
| B 目标版（推荐） | 解决根因、兼顾成本 | 推荐理由与适用条件 |
| C 彻底版 | 重构式解法 | 何时值得付出这个成本 |

要求：

- 三版必须**沿决策轴拉开差异**（成本 / 风险 / 扩展性），不能是同一方案的三种措辞。
- 每版写清：影响面、成本量级、风险、回滚难度。
- 小改动不表演三版：一版 + 一句话说明被放弃的备选及原因即可。

## 4. 问题定义审查：不要默认题面是对的

### 4.1 回到目标与约束

剥离「目前是这么做的」，回答三个问题：

1. **要达成什么？**（目标）
2. **受什么约束？**（兼容、合规、人力、时间、既有契约）
3. **不解决会怎样？**（代价与紧迫性）

若三者与题面矛盾，优先相信目标与约束，而不是题面里的实现方式。

### 4.2 三组辨析

| 辨析 | 提问 | 典型误判 |
|---|---|---|
| 症状 vs 病因 | 连问 2–3 层「为什么」，问题在哪一层可以被真正干预？ | 给慢查询加缓存，掩盖了索引缺失 |
| 手段 vs 目标 | 用户要的是这个动作，还是这个动作背后的结果？ | 「加个开关」，真实目标是「可控地回滚」 |
| 局部 vs 系统 | 问题发生在哪个环节，谁在为它买单？ | 调用方做兜底，根因是契约不一致 |

### 4.3 允许改题，但必须明说

- 发现更值得解决的问题：直接指出，给出证据与影响对比（原问题 vs 新问题）。
- 提出建议并等待确认；**不擅自改题，也不沉默执行表面需求**。
- 用户坚持原题时，按要求执行，并在交付中保留「根因仍未解决」的提示。

## 5. 本节反模式

| 反模式 | 为什么错 | 替代做法 |
|---|---|---|
| 把用户的话当需求终稿直接开写 | 可能把手段当目标 | 先做问题定义审查 |
| 三版方案只有措辞差异 | 表演思考，浪费对齐成本 | 沿决策轴拉开差异，或只给一版 |
| 每步都问用户 | 打断协作节奏 | 对齐一次，范围锁定后自主执行 |
| 猜一个需求就开写 | 返工成本远高于一次提问 | 影响正确性的歧义必须先问 |
