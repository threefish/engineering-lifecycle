# 架构分层与依赖方向

> 加载时机：新增文件、决定代码放哪一层、跨模块调用、重构结构调整前读取。出方案时也要先对照本文件，避免规划出违规结构。

## 1. 层的职责

| 层 | 放什么 | 禁止什么 |
|---|---|---|
| 入口 / 启动 | 进程启动、模块装配、环境配置加载 | 业务逻辑 |
| 门面 | 路由、参数接收与校验、权限与日志标记、转发 | 业务逻辑、事务、直接访问数据访问层 |
| 业务 | 业务规则、流程编排、事务边界、事件发布、调用数据访问与外部集成 | 传输协议类型、手工拼 SQL、直接依赖外部存储细节 |
| 基础设施 | 数据访问实现、存储实体、对象转换、缓存与消息等技术适配 | 业务规则 |
| 模型 | 请求 / 响应对象、DTO、枚举、常量、错误码定义 | 行为逻辑（纯映射方法除外） |
| 公共内核 | 统一返回体、异常内核、分页、审计基类、通用工具 | 具体业务逻辑 |
| 外部集成（防腐层） | 外部系统客户端、外部请求 / 响应模型、异常归一化 | 业务规则、被业务层反向依赖 |

## 2. 依赖方向

依赖只能沿一个方向：**入口 → 门面 → 业务 → 基础设施 → 公共内核 / 模型**；外部集成只依赖公共内核与模型；模型只依赖公共内核。

- 禁止反向依赖与跨层调用；门面直接注入数据访问层、基础设施引用业务层，均属架构违规。
- 业务层不得感知传输协议（HTTP / RPC / MQ 的具体类型）。
- 同一概念只在一层落地，不在多层重复定义。

## 3. 小项目降级

不拆物理模块时，**包结构必须保持同样的分层与依赖方向**。禁止按功能纵向共置（把路由、业务、存储塞进同一个功能包）。

## 4. 落位判断顺序

1. 这段逻辑是规则、编排，还是纯技术适配？
2. 它需要感知外部协议或存储细节吗？（需要 → 下沉到防腐层或基础设施）
3. 它引入的是新机制，还是复用公共内核既有能力？（新机制 → 先说明必要性）
4. 依赖箭头方向是否仍然单向向下？
