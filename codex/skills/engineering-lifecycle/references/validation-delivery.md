# 验证、交付与完成定义

> 加载时机：改动完成、准备交付说明或判定任务完成前读取。

## 1. 必须验证

- 能编译就编译，能测试就测试，能运行就运行；不跳过可用的验证手段。
- 按风险与档位选择验证深度：
  - 轻量改动：至少通过编译 / 静态检查。
  - 行为变更：必须有可复现的验证路径（用例、复现步骤或接口调用）。
  - Bug 修复：先复现、后验证修复。
  - 重构：必须有兼容性验证（行为等价证据）。
- 不得仅凭「代码看起来正确」宣称完成。

## 2. 修改后自检

- 无语法、编译或类型错误。
- 无新增未使用的变量、方法或依赖。
- 无明显空指针、非法参数、越界等基础问题。
- 无敏感信息或硬编码配置、密钥、环境地址。
- 无需求之外的代码变更；原有行为未被无意改变。
- 分层与依赖方向未被破坏。

## 3. 失败重试

- 同类编译、测试或逻辑错误连续修复**不得超过 2 次**。
- 无法解决时按 `escalation.md` 的格式说明：当前问题、已尝试方案、失败原因、需要用户提供的信息。
- 禁止无意义循环修改。

## 4. 无法验证时

- 说明原因与替代证据：代码路径分析、同类先例、手工验证步骤。
- 不得默认通过，不得虚构测试结果。

## 5. 交付说明

结论先行，证据随后。每次交付必须包含：

| 项 | 要求 |
|---|---|
| 结论 | 一句话说清做了什么、是否达成预期 |
| 变更 | 关键文件与改动范围 |
| 证据 | 文件与行号、命令、输出、测试结果；他人可复现 |
| 验证状态 | 已编译验证 / 已运行验证 / 未验证，逐一严格区分 |
| 影响与风险 | 影响面、已知风险（含未采纳的反方意见与理由）、剩余不确定性 |
| 回滚 | 出问题时如何退回 |

禁止：虚构测试结果、把「没跑」说成「通过」、隐藏失败、用模糊措辞掩盖不确定性。

## 6. 完成定义（Definition of Done）

- 实现与需求、Non-goals 一致，无范围蔓延。
- 分层与依赖方向未被破坏。
- 输入校验、错误码、统一返回结构保持一致。
- 安全红线逐条核对通过。
- 数据变更可迁移、可回滚；查询有边界。
- 验证证据齐备，状态标注如实。
- 公共契约与相关文档同步更新。
- 无调试残留、临时文件、硬编码配置。

## 7. Code Review 模式

- 只评审，不直接修改被评审代码；不输出可直接覆盖原文件的完整代码。
- 不以「优化」为名扩大范围，不批量追责历史遗留，不因个人风格偏好要求修改。
- 必须关注：功能逻辑（需求、边界、状态、异常分支）、安全（注入、越权、泄露）、性能（N+1、全表扫描、大对象）、工程规范（对照 `SKILL.md` 产出红线与相关 reference）、可维护性（重复、过度抽象）、兼容性。
- 每条问题包含：**位置、问题、影响、改进方向**。分级：
  - **Blocker**：功能不可用或严重安全 / 数据一致性风险，必须修复。
  - **Critical**：显著影响正确性、稳定性、性能或可维护性，建议修复后合并。
  - **Minor**：非阻断，可选优化。
  - **Info**：补充说明或建议，不要求修改。
- Review 结论不得把个人偏好描述为强制规范。
