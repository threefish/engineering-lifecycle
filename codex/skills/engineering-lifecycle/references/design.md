# 方案设计与反方审议

> 加载时机：非平凡改动（标准档及以上）在方案定稿前读取。轻量改动不必加载。

## 1. 影响推演六维

任何非平凡改动，动手前过一遍：

| 维度 | 要回答的问题 |
|---|---|
| 直接效果 | 改完后立刻改变什么？如何验证？ |
| 模块与契约 | 谁依赖它？接口 / 数据 / 事件 / 配置的兼容性是否被破坏？ |
| 用户行为 | 使用者会因此改变什么习惯？误用会怎样？ |
| 系统复杂度 | 新增了几个概念、几条路径、几个状态？是否可逆？ |
| 长期维护 | 一年后还有人能理解它吗？测试与文档成本是多少？ |
| 回滚成本 | 出问题时多快能退回？有没有不可逆副作用（数据 / 消息）？ |

输出：影响清单 + Non-goals + 回滚方式。**只写直接效果的方案，视为未完成推演。**

## 2. 与分层约束对照

方案必须落在 [references/architecture.md](references/architecture.md) 的分层与依赖方向之内：

- 新逻辑落在哪一层，是否需要新的跨层依赖（需要即为架构违规）。
- 是否新增机制；既有统一返回、异常、分页、审计、锁、配置能否复用。
- 契约变更范围：路径、字段、事件、配置项是否受影响。

## 3. 跨领域类比

遇到结构性难题时，主动检索其他领域已验证的解法：

- 数据库 → 事务、补偿、幂等
- 编译器 → 分阶段校验、先解析后执行
- 制造业 → 防呆设计（让错误无法发生，而非事后检查）
- 运维 → 可观测性、灰度、熔断
- 航空 → 检查单、双人复核

要求：说明类比的**映射关系与失效边界**，不能只借名词。

## 4. 简单性检验

- 更小的改动能否达到 80% 的效果？
- 新增的抽象是否已有第二个使用者？没有就是过度设计。
- 能否靠删除代码解决问题？删除优先于新增。
- 重复可以被容忍，错误的抽象不能。

## 5. 反方审议：先假设自己错了

方案定稿前，强制切换到「最强反对者」视角，集中完成一次，产出 3–5 条要点：

1. **如果这个方案是错的，最可能因为什么？**
2. **有没有反例或边界条件能推翻它？**（极端输入、并发、空数据、旧版本兼容）
3. **反对者会拿什么证据攻击它？** 这些证据现在存在吗？
4. **替代方案里有没有更简单的？** 为什么没选？
5. **失败的最早信号是什么？** 上线后看哪个指标能第一时间发现？

结论二选一：

- 反方证据成立 → 修改方案，重新过影响推演。
- 反方证据不成立 → 在交付说明中保留「已知风险与不采纳理由」。

反方审议不是自我怀疑到瘫痪：一次完成，有结论即停。

## 6. 本节反模式

| 反模式 | 为什么错 | 替代做法 |
|---|---|---|
| 只分析直接效果 | 二阶影响在交付后爆炸 | 过六维影响推演 |
| 反方审议走过场 | 没有可证伪的观点 | 写出「最可能失败的原因」与早期信号 |
| 为单一使用者建抽象 | 增加永久维护成本 | 先重复，出现第二个使用者再抽象 |
| 以「更优雅」为由扩大改动 | 超出范围、放大风险 | 回到目标与约束，最小改动优先 |
